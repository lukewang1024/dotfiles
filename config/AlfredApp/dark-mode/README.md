# Dark Mode — Alfred workflow

Toggle the macOS light/dark appearance from Alfred. Replaces
[alfred-dark-mode](https://github.com/sindresorhus/alfred-dark-mode) by Sindre
Sorhus (2017, bundle id `com.sindresorhus.dark-mode`), which shipped 2.5 MB —
a 112 KB icon and 70 unused `node_modules` packages — to run four lines of
AppleScript.

## Commands

| Keyword | Effect |
| --- | --- |
| `dark` | Switch to the other appearance |
| `dark light` | Force light |
| `dark dark` | Force dark |

The Script Filter's first row is the toggle, so the old muscle memory (`dark` ↩)
still does exactly what it used to.

## Why it only flips the OS switch

`apply.sh` sets the system appearance and stops there. It deliberately does *not*
fan out to nvim / tmux / Alacritty / devboxes, even though that is what the human
actually wants to happen — because that fan-out already exists and is not
Alfred's to own:

- **`util/shell/appearance-daemon`** runs `dark-notify` as a LaunchAgent
  (`com.lukew.appearance`). On every macOS appearance change it writes
  `$XDG_STATE_HOME/appearance` (nvim's libuv watcher flips `&background` live;
  plain vim on its next `FocusGained`), swaps Alacritty's imported theme, and
  relays to every attached SSH devbox via `theme-push-remotes`.
- **tmux-dark-notify** drives the tmux side through
  `config/tmux/appearance-{light,dark}.conf`.

Both hang off the OS appearance, which is the one thing every *other* way of
changing the theme — Control Centre, System Settings, the sunrise/sunset auto
schedule — also moves. Re-implementing the fan-out here would give the Alfred
path a private second-best copy of a chain that is already correct, and would
silently rot the moment the real chain changed.

The Script Filter's subtitle reports what is actually listening (`nvim,
Alacritty, 2 devboxes follow`), counted from `launchctl list com.lukew.appearance`
and `~/.ssh/tmux-*.sock`, so a broken relay is visible before you wonder why nvim
didn't follow.

**Fallback:** on a machine where `appearance-daemon install` was never run,
nothing is listening, so `apply.sh` calls `theme-sync <want>` directly — the same
reconcile the daemon would have triggered. It self-gates on `launchctl list`, so
this stays off wherever the daemon *is* loaded.

## Install

Nothing to run. Alfred's sync folder is `~/.dotfiles/config/AlfredApp`, and
`Alfred.alfredpreferences/workflows/user.workflow.dark-mode` is a repo-relative
symlink back to this directory — both are tracked, so a fresh clone is already
wired up. See `../README.md`.

Alfred caches `info.plist` in memory, so **restart Alfred** after changing it:

```sh
osascript -e 'tell application "Alfred 5" to quit'; open -a "Alfred 5"
```

`filter.py` and `apply.sh` are read live on each run and need no restart.

## Notes for future edits

- `filter.py` is pinned to `/usr/bin/python3` (system 3.9) for the same reason as
  `../amphetamine`: `python3` on `PATH` is a pyenv shim that Alfred's environment
  does not reliably resolve. No 3.10+ syntax.
- `AppleInterfaceStyle` reads `Dark` in dark mode and is **absent** in light mode
  — there is no `Light` value. `defaults read` exiting non-zero *is* the light
  signal, not an error.
- Setting `dark mode` via System Events needs Alfred to hold Automation
  permission for System Events; `apply.sh` reports that explicitly rather than
  failing silently.
- Setting light or dark explicitly turns **off** macOS's "Auto" appearance
  schedule. There is no AppleScript verb to put it back — that is a System
  Settings-only control — so the workflow does not pretend to offer `dark auto`.
- `icon.png` is generated by `make-icon.sh` (SVG → `rsvg-convert`), same approach
  as `../lark-docs/make-icons.sh`.
